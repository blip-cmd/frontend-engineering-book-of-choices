## LinkedIn

I've opened up a project I've been building: **Frontend Engineering as a Book of Choices**, a free reference for frontend architecture decisions.

Most guides tell you which framework to use. This one starts from your constraints: does the page need to rank on Google, is the data personalised, does it update dozens of times a second, does it have to work offline? Then it walks through the options that fit and what each one costs.

What's in it:
• 9 chapters: rendering, reactivity, state, APIs, design systems, styling, delivery, local-first
• 5 decision playbooks for common product types
• A free calculator: answer six questions, get a starting architecture with the reasoning, and share the result as a link

One thing I want to be upfront about: the first draft was written with AI tools. Instead of hiding that, every page is now being verified in the open. Each claim is checked against official docs (MDN, OWASP, web.dev, framework docs), and an independent second check can fail the page. The claim-by-claim ledger is public, and each page says whether it is still a draft.

The first verified page is a production security checklist. Verifying it caught a dangerous claim in the draft about a popular library, which is exactly why this process exists.

If you work on frontends, I'd value your corrections and your real-world trade-offs: "we chose X, and this is what it cost us".
