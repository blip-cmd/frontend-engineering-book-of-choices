## 1. The Vulnerability Landscape in Client Applications

Because frontend code executes within the user's untrusted browser environment, security boundaries must be strictly defended at every layer of asset delivery and user input processing:

1. **Cross-Site Scripting (XSS):**
   * *Mechanism:* An attacker injects malicious JavaScript into the application. If executed, the script accesses session tokens, logs keystrokes, or silently performs actions on behalf of the victim.
   * *Variants:* Stored XSS (saved in database and rendered to other users), Reflected XSS (reflected off URL queries), and DOM-based XSS (unsafe DOM manipulation like `element.innerHTML = userInput`).
2. **Cross-Site Request Forgery (CSRF):**
   * *Mechanism:* An attacker lures a logged-in user to an external site that submits unauthorized commands to a vulnerable target application where the user is authenticated via ambient credentials (cookies).
3. **Supply-Chain Dependency Poisoning:**
   * *Mechanism:* Malicious code introduced via compromised open-source npm dependencies or typo-squatted package names.

## 2. Architectural Hardening Strategies

### Strategy A: Strict Nonce-Based Content Security Policy (CSP)
* **What it does:** A response HTTP header (`Content-Security-Policy`) that instructs the browser to execute only scripts carrying a cryptographically secure, per-request nonce generated by the server:
  ```http
  Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-rAnd0m123' 'strict-dynamic'; object-src 'none'; base-uri 'none';
  ```
* **Why it matters:** Even if an attacker injects `<script>maliciousCode()</script>` into the DOM, the browser refuses to execute it because it lacks the valid server nonce.

### Strategy B: Secure Cookie Hygiene & Token Storage
* **The Rule:** Never store sensitive authentication or session tokens in `localStorage` or `sessionStorage`. Any XSS vulnerability can immediately steal tokens from storage APIs.
* **The Defense:** Store session tokens in `HttpOnly`, `Secure`, `SameSite=Lax` (or `SameSite=Strict`) cookies. JavaScript running in the browser cannot read `HttpOnly` cookies, completely neutralizing client-side token exfiltration.

### Strategy C: Safe DOM Manipulation and Sanitization
* **The Rule:** Avoid `dangerouslySetInnerHTML` in React or direct `innerHTML` assignments in vanilla JS.
* **The Defense:** When rendering rich-text HTML (e.g., from a CMS or markdown parser), always sanitize the raw markup using audited libraries like `DOMPurify` before mounting to the DOM.

## 3. Defense Matrix

| Threat Vector | Primary Vulnerability Trigger | Architectural Defense | Verification Tooling |
| :--- | :--- | :--- | :--- |
| **DOM-based XSS** | `innerHTML`, `document.write`, unescaped markdown | Use text bindings or sanitize with DOMPurify | Semgrep, ESLint `react/no-danger` |
| **Inline Script Injection**| Script tags reflected from queries or inputs | Strict Nonce-based Content Security Policy (CSP) | CSP Evaluator (Google), Mozilla Observatory |
| **Session Theft** | Storing JWTs or API keys in `localStorage` | Migrate session tokens to `HttpOnly` cookies | Browser DevTools Application audit |
| **Clickjacking** | Embedding app within hidden `<iframe>` overlays | `Content-Security-Policy: frame-ancestors 'none'` | SecurityHeaders.com, OWASP ZAP |
| **Supply Chain Hijacking**| Unvetted transitive npm dependencies | Lockfiles, automated auditing (Socket, Snyk, npm audit) | Snyk Code Scan, Socket.dev CLI |

## 4. Production Checklist Before Deployment
* [ ] Verify that all cookies carrying session identifiers set `HttpOnly; Secure; SameSite=Lax`.
* [ ] Implement an automated dependency scanner in CI to reject packages with known high-severity CVEs.
* [ ] Enforce Subresource Integrity (SRI) on external scripts loaded from public CDNs.
* [ ] Ensure all markdown parsers or rich-text renderers pass output through `DOMPurify.sanitize()`.
